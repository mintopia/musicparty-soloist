# The Config File is UI-editable YAML; environment configuration is removed

The original model (ADR-0009 and earlier) held the Config File static and made every value
env-overridable via `${VAR}` interpolation, so operators configured mostly through the
environment. We are replacing that: the Config File is now the single source of truth,
editable both by hand and through the Landing Page, and **all environment configuration is
removed** — no `${VAR}` interpolation, no env overrides. This gives a self-hosted party tool
a real setup experience (edit in a browser, save, done) instead of hand-assembled env vars.

The Landing Page writes the file back with the `yaml` Document API so hand-written comments
survive, validates the incoming config before writing (never persisting a file that would
fail to boot), and writes atomically (temp + rename) so a crash mid-save can't corrupt a
bind-mounted file. In Docker the file is bind-mounted at `/config/config.yaml`; the path is
otherwise the `--config` flag (default `./config.yaml`).

## Considered Options

- **Keep env overrides, add UI writing on top** — rejected. Round-tripping `${VAR}` through a
  file the UI rewrites is ambiguous (persist the literal or the resolved value?), and a
  half-removed env layer is more confusing than none.
- **UI-editable YAML, env removed** (chosen) — one authoritative file, one mental model.

## Consequences

- **Breaking change.** Existing deployments that configure via env / `${VAR}` must move those
  values into the Config File. Called out in the release notes; `.env.example` is dropped.
- **Secrets now live in the file in cleartext** — API Key, Auth Token, Read-only Token, web
  password. Accepted: it is a self-hosted single-container tool and the file sits on the
  operator's host with their other secrets. The `session_secret` and `readonly_token` are
  autogenerated and persisted into the file on first write / boot if absent (this also fixes
  the earlier "regenerate every boot" churn).
- **First-run bootstrap.** With no env, initial web credentials can't come from outside, so
  when the Config File has no web credentials the Proxy serves an unauthenticated **Setup
  Page** that sets only the username and password, then writes the file; everything else
  fails closed and Soloist is not started until configured. This supersedes the
  "env-overridable credentials" note in ADR-0009 — the credential *mechanism* (login form +
  signed cookie) is unchanged; only their *source* changes to the file + Setup Page.
- **Apply model.** Config is still read once at boot. On save: hot fields (tokens, webhooks,
  autoplay, Overlay Config) and Audio Output links apply live; Soloist-arg changes are
  persisted but not auto-applied — the UI shows a "restart soloist to apply (interrupts
  playback)" banner with a button, so playback is never interrupted without the operator's
  say-so. `proxy.listen`, `soloist.extra_args`, and `soloist.data_dir` are shown read-only in
  the UI (lockout / structural footguns) and remain hand-edit-only.
