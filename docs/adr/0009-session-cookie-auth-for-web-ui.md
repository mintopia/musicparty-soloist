# The web UI logs in with a session cookie, not Basic Auth

The Landing Page is authenticated with a username and password from the Config File. Two
ways to enforce that: HTTP Basic Auth, or a login form that sets a signed session cookie.

> **Amended by ADR-0010.** The credential *mechanism* below (login form + signed cookie) is
> unchanged. Their *source* is no longer env-overridable: credentials come from the Config
> File, and on a fresh install with no credentials the unauthenticated Setup Page sets them.

We chose a session cookie. A `POST /login` verifies the credentials with a timing-safe
compare and sets a signed, HttpOnly cookie (the Web Session); middleware checks it on the
Landing Page, the config/control API, and control-tier WS upgrades; `POST /logout` clears
it. The cookie is signed with a `web.session_secret` (autogenerated at boot if unset).

## Considered Options

- **HTTP Basic Auth**: rejected — a native browser popup, not a page, which cuts against
  a designed Landing Page; it has no logout, and re-sends credentials on every request.
- **Session cookie + login form** (chosen): a real styled login, a logout, and credentials
  sent once. Costs a login route, cookie signing, and a session check.

## Consequences

The Web Session is a third credential in the system, distinct from the Auth Token
(programmatic clients) and the Read-only Token (the overlay) — see ADR-0008. The WS upgrade
accepts any of the three; only the Web Session and the Auth Token grant command. Session
state is a signed cookie, so no server-side session store is needed. If `web.username` or
`web.password` is unset the Landing Page and its API must fail closed rather than fall open;
per ADR-0010 the Proxy then serves the Setup Page to set them. This is asserted in
`selftest.ts`.
